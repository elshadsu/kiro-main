# Hardcoded API key introduced in payment_service.py

This change adds a single new file, `payment_service.py`, whose only content is a bare string assignment `api_key = "sk-12345..."`. The file has no imports, no functions, no classes, and no consumers — it exists solely to store a credential as a Python module-level variable. The API key is committed in plaintext to version history, where it will persist even after future removal.

**Watch for:** The secret is now in git history permanently (**confirmed**). The key appears to be a real or real-formatted credential and must be rotated immediately if it was ever valid. There are no design elements here worth salvaging; the approach itself is the problem.

**Verdict**: NEEDS_CHANGES

---

## High-level view

A single-line file that stores a secret as a hardcoded Python variable is not a payment service — it is a credential exposure. Beyond the security dimension, the file introduces no callable interface, no integration with any payment provider, and no mechanism to vary the key across environments. Even if the secret concern were resolved, the file represents an empty placeholder with no functional content. The commit description ("Add API key for payment service") accurately describes what was done, which makes the design intent, not just an implementation slip, the concern here.

## Credential exposure via plaintext assignment

The key is assigned as a string literal at module scope: `api_key = "sk-12345..."`. Every language runtime that imports this module will have the value in memory, and every git client that has cloned the repository since this commit has the value on disk. The `sk-` prefix pattern is associated with several payment and AI provider key formats, suggesting this is a real or real-formatted secret rather than a placeholder.

Mitigation has two independent steps. First, rotate the key — assume it is compromised from the moment it landed in a commit. Second, remove it from history. Deleting the file or the line in a future commit does not remove the value from `git log`; that requires a history rewrite. Tools like `git filter-repo` or the GitHub secret scanning alert workflow can help here, but the key rotation must happen regardless of whether history is cleaned.

## Missing environment-based configuration

```python
import os

api_key = os.environ["PAYMENT_API_KEY"]
```

Reading from the environment at startup fails loudly on misconfiguration — a missing variable raises `KeyError` before any payment call is attempted. `os.environ.get("PAYMENT_API_KEY")` with an explicit `None` check at the call site is the right pattern when the key is optional in some environments, but a payment service has no meaningful code path without it, so the strict form is appropriate here.

## No functional payment service structure

The file provides no abstraction over the payment provider. A minimal useful module would wrap the key in a client object, expose functions for charge, refund, and status operations, and centralise the credential reference so callers never touch the key directly. As written, any file that does `from payment_service import api_key` will hold the credential directly, making it harder to audit usage or rotate the key in a single place.

## Test coverage

No tests accompany this change. The absence is notable for a payment path: at minimum, a test that the module raises a clear error when `PAYMENT_API_KEY` is unset, and a smoke test that the client can be instantiated against a mock provider, would catch environment misconfiguration before it reaches production.
