# Hardcoded API key introduced in payment service

A new file `payment_service.py` is added with a single line: a bare string
assignment of an API key (`sk-12345...`). There is no surrounding code, no
abstraction, no env-var lookup — just a credential committed directly to the
repository. This is a critical security failure. The secret is now part of
the repository history permanently, regardless of any subsequent deletion,
because git history is append-only and the commit is already merged into
`main`.

**Watch for:** The API key `sk-12345...` is now embedded in `main`'s git
history and must be treated as compromised. Rotate it immediately via the
payment provider's dashboard.

**Verdict**: NEEDS_CHANGES

---

## High-level view

A live credential has been committed to source control. The file contains
nothing but the key assignment — no service call, no configuration loading,
no abstraction — so there is no path forward that salvages this file as
written. The key must be rotated now regardless of what happens to the code,
because the commit hash is permanent in `main`'s history. Even if the file
is deleted in a follow-up commit, any clone, fork, or CI artifact that ran
against this commit may already hold the key.

The correct pattern for secrets in a Python service is
`os.environ["PAYMENT_API_KEY"]` or a secrets manager call at runtime. The
key never appears in source.

---

## Issues

1. **Hardcoded credential in source** — `api_key = "sk-12345..."` is a live
   secret committed to `main`. Rotate this key immediately via the payment
   provider's dashboard; assume it is compromised. Remove the file and
   replace with an env-var lookup (`os.environ["PAYMENT_API_KEY"]`) or a
   secrets manager call.

2. **Permanent history exposure** — Deleting or overwriting the file in a
   future commit does not remove the secret from git history. If this
   repository is or becomes public, the key is permanently exposed. Run
   `git filter-repo` (or BFG Repo Cleaner) to scrub the commit from
   history, coordinating with all existing clones and forks.

3. **No secret scanning gate** — This commit passed merge without triggering
   a credential scanner. Add a pre-receive hook or a CI step (e.g.,
   `git-secrets`, `trufflehog`, or GitHub's built-in secret scanning) to
   block future commits containing secret patterns before they reach `main`.

## Details

### Hardcoded credential and permanent history exposure

The key is now recorded in the git object store at the commit that merged
this into `main`. Even after a `git rm`, the original blob remains reachable
via the commit hash and any ref — branch, tag, reflog entry, fork, CI cache,
or mirror — that pointed to `main` after this merge. **Confirmed**: the diff
shows `+api_key = "sk-12345..."` as the only line in the new file.

Remediation sequence:

1. Rotate the key immediately via the payment provider. Do not wait for the
   code fix.
2. Remove the file and replace with `os.environ["PAYMENT_API_KEY"]` (or a
   secrets manager SDK call).
3. Scrub the commit from history using
   `git filter-repo --path payment_service.py --invert-paths` and
   force-push, coordinating with all collaborators holding clones.
4. Audit CI logs, build artifacts, and deployment environments to verify the
   old key value does not persist.

### Absent secret scanning gate

**Confirmed**: this commit reached `main` without being blocked. The diff
contains a string matching the `sk-` prefix pattern used by several payment
and AI API providers. Standard secret scanning tools (GitHub's native
scanner, `trufflehog`, `git-secrets`) would have flagged this pattern at
push time. The absence of any such gate is a process gap independent of this
specific commit.

### No functional code

The file introduces a credential but no behavior. There is no import of an
HTTP client, no function, no use of the key. This means the commit is purely
credential exposure with zero delivered functionality — it has no redeeming
production value that would need to be preserved during remediation.
